# 动画制作：像素与高清共用

本教程以帧动画 V2（`meowa-animation-run`）为主，适用于 Pixel 和 HD。先完成[角色设计与验收](character-design.md)，再依次准备动作姿态、画布和帧约束，生成小样、验收、整理与交付。静态角色任务不必进入本流程。

先确定动作的用途、方向、单次或循环、是否需要控制终点，以及交付格式。每一步只在已有预算和执行授权内进行；任务恢复、输出目录与最终产物边界遵循[运行与产物规则](../../references/running-and-outputs.md)。以下命令从 Skill 仓库根执行，安装版换成实际 runner 路径；`<...>` 为待替换值，下一步输入从任务子目录的 `final_outputs.json` 获取。

## 1. 准备动作姿态与首尾帧

### 生成前确认背景用途

生成前先与用户确认：使用绿幕去背景、不用绿幕但需要去背景，还是用于宣传展示、无需抠图。用户已明确背景用途时直接沿用，不重复询问。

- **免费绿幕抠图：** 使用绿色背景，先按下节准备干净透明母版再填绿；生成时关闭付费抠图，后续使用官网免费抠图工坊。
- **不用绿幕但需要去背景：** 按素材准备背景与去背景方案，帧率建议见[高帧率选择](#4-生成小样高帧率与分辨率)。
- **宣传展示、无需抠图：** 建议纯白背景，输入与首尾帧统一白底；生成时显式设置 `--remove-bg-method none --background-color '#ffffff'`，并检查结果全程保持白底。已有透明母版可直接填白，无需先做绿幕。

绿幕只在需要透明背景时使用：抠绿后边缘可能残留绿色溢色或抠不干净，宣传展示不需要承担这个风险。

### 先准备透明角色图，再填充绿幕

**用绿幕制作角色帧动画前，必须先完成生成图片的去背景与透明边缘验收，再填充绿幕。** 不能把带原背景的角色图直接铺到绿色底图上：原背景、白边和轮廓杂色会留在主体周围，并被动画生成带入后续帧，容易出现大量边缘残留；动画生成后再抠绿幕也很难清除这些非绿色残边。

采用绿幕流程时，角色母版尽量从第一次生图就输出透明背景，方便在确定动作画布后填充统一纯色。Image2.5 生图／编辑时开启 `--remove-bg-method standard`，去背景不收附加费；生成与参考图仍正常计费。已得到干净透明图时无需重复抠图，但必须检查实际 alpha 和轮廓；仅有透明通道或传入了去背景参数，不代表背景已清理干净。

已有角色图不透明时，先选择一种方式得到干净的透明角色：

- **单独去背景：** 用 `remove-background-run`，按原图选择 `--mode pixel|hd`。普通去背景效果不佳时，可在授权预算内尝试高级去背景（`--quality advanced`）；各模式的档位与输入条件不同，按[去背景说明](../../references/pixel-and-hd-assets.md#background-removal)选择。Pixel 高级去背景要求纯色源背景并传入准确背景色；需要像素清理的图先完成像素化，再抠图。
- **Image2.5 重绘去背景：** 用万能编辑选择 `--generation-model image-2.5` 并开启 `--remove-bg-method standard`，提示“输出与参考图一模一样的角色，保持外观、姿态、配色和构图，只去掉背景，输出透明背景”。这是可尝试的洗图路线；编辑本身仍计费，也可能改变原图，不能保证逐像素一致。对照原图检查身份、细节、像素网格、尺寸与锚点，必须精确保留原像素时优先单独去背景。详见[Image2.5 透明素材说明](../../references/pixel-and-hd-assets.md#image25-transparent-asset-tips)。

透明图验收后，在同尺寸画布的底层填充绿幕，不覆盖主体，也不缩放角色。通常用 `#00b140`；主体含重要绿色时换成能分离的纯色。**去背景后和填色后都要实际打开检查：** 看发丝、衣摆、武器间隙与半透明区域是否残留原背景、误删主体或出现白边／杂色边；填绿后更容易暴露的残边应先修正或更换抠图方式，再付费生成动画。首尾帧使用一致背景；空白帧直接用相同纯色画布。设置动画命令的 `--background-color` 不能清除输入图已有的不透明背景。

### 准备并复核动作姿态

普通动作通常只需首帧；需要严格限定起止状态时用首尾帧控制，再通过动作描述约束过程。用万能编辑（`image-edit-run`）获得动作需要的姿态：

```bash
python3 skills/game-assets/meowart_api.py image-edit-run \
  --reference-image <approved-character.png> \
  --prompt "保持角色、配色和绘制风格，将姿态改为向右挥剑前的蓄力，保持脚底锚点" \
  --mode hd --generation-model image-2.5 --remove-bg-method standard \
  --output-dir ./outputs/knight-attack-pose
```

示例为高清编辑并请求免费原生去背景；像素素材使用 `--mode pixel`，模型按像素编辑需求选择。不要给大幅改姿态默认加 `--strict`；该选项适合必须严格保持像素结构的编辑。编辑后再次验收形象、真实尺寸、脚底位置与透明边缘；编辑可能重新引入背景，必要时按上面的流程清理。姿态和画布确定后，按已确认背景统一填色并检查；采用绿幕时，避免已清理的母版在后续编辑中又带回杂背景。

角色有容易在动作中丢失的独特特征时，在姿态编辑和动画提示词中简短写明，不只依赖参考图。例如“没有五官的人形，面部光滑，没有眼睛、鼻子和嘴”，或“面部只有一只巨大的竖眼，没有其他五官”。沿用已定稿的特征，不额外改设计；生成后仍需检查动作中是否保持。

根据动作选择帧约束：

| 动画目标 | 首帧 | 尾帧与动作描述 |
|---|---|---|
| 单次攻击 | 对应招式的准备姿态 | 通常只需首帧；描述出招一次并收势，使用非循环动作设计 |
| 行走或可重复动作 | 双腿一前一后的行走姿态，或对应动作的准备姿态 | 通常只需首帧；描述完成一轮并衔接下一轮 |
| 角色变身 | 原形态 | 用万能编辑生成变身后形态作为尾帧，描述一次清晰的变身 |
| 特效凭空出现 | 空白帧 | 特效成形图作为尾帧，描述特效从无到有出现 |
| 特效消散 | 特效成形图 | 空白帧作为尾帧，描述特效逐渐消失 |

空白帧使用与目标背景相同的纯色画布，例如绿幕；首尾帧必须保持相同尺寸、背景、视角和锚点。变身造成体型或武器变大时，为两帧统一增加足够的画布空间，不要分别缩放角色。首尾帧控制用于过渡，不强求循环。

## 2. 按动作方向选择画布与留白

**先估算动作的运动范围，再选画布比例；不要把整套动作放进同一个最大方形画布。** 原地行走不需要为向前移动预留半张画布，复杂连击也不代表需要增加头顶空间。无效空白会让角色在相同生成分辨率下占用更少细节；720P／1080P是生成清晰度档位，不要求输入也做成720px或方形。

先验收动作起始姿势，量出角色、装备和已持道具的内容边界，再估算全程最远的拳脚、武器、投射物和特效范围。以内容边界的宽高`w × h`为基准，分别决定左、右、上、下余量，画布为`(w + 左 + 右) × (h + 上 + 下)`。先去掉不需要的旧留白，避免在已扩大的母版上重复加padding；保持已验收的角色尺度，不靠缩小角色腾空间。

| 动作 | 优先留出的空间 | 常见的浪费 |
|---|---|---|
| 原地待机、行走、奔跑 | 少量四边余量，覆盖摆臂、迈腿和身体起伏 | 把朝向误当成整个人要横穿画面，在前方留大块空白 |
| 轻攻击、重攻击、复杂连击 | 朝向前方的横向空间，覆盖拳脚、前探和武器；上方仅在上勾拳等动作确需时增加 | 因为动作复杂就把画布加高，头顶长期空着 |
| 投掷 | 肩后蓄力与前方出手轨迹；投射物允许飞出画面时，不必容纳无限远的飞行 | 只增加头顶，或为了整个弹道把角色塞进极宽空画布 |
| 跳跃 | 按跳高增加上方空间，底部留落地缓冲；原地跳不额外铺开横向 | 对所有动作都套用跳跃画布 |
| 跳起飞扑、俯冲砸地 | 同时估算竖直轨迹、向前位移和落地冲击范围，按实际轨迹选比例 | 只看静态站姿，或四边等量盲加 |
| 旋转、龙卷风 | 按伸臂后的旋转半径及气流范围留空间 | 没有上升动作却预留大段头顶空白 |

例如内容边界约`96×192px`、朝左的角色，可以从行走`120×208`（左右各12、上下各8）、横向连击`240×216`（左132、右12、上下各12）、跳跃`144×304`（左右各24、上96、下16）这类不同画幅开始估算。它们只是说明比例和四向分配的例子，不是默认参数或完整入框保证；实际按准备好的姿势、动作幅度和入口限制调整。跳跃的上方空间可先按角色身高约一半估算，再检查是否够用。

**付费提交前打开每种动作的输入图检查。** 解释得出每个大块空白将被哪一阶段动作使用；若连击头顶空着大半、行走前方空着大半，却没有相应轨迹，就先收紧那一方向。确认完整轮廓、动作所需范围、少量安全边距和脚底／身体锚点，不把“未超过入口尺寸上限”当成画布已经合适。

**先试一两个代表动作，再逐批扩大。** 不要因为允许并发，就一开始提交整套动画。首轮选1～2个能暴露画布问题的动作，例如一个行走或出拳，以及一个运动范围较大的动作；检查整段动画是否够用、有无越界截断、是否留下大块无效空白，再调整画幅、四向余量和起始姿势。确认这一类动作的准备方式可用后，才逐步增加同类动作的数量，并遵守用户授权的并发与预算。行走通过不能证明跳跃、投掷或龙卷风也适用；切换运动方向或幅度明显不同的动作时，先做新的小样。试片验收顺序见[动画校验](#6-动画校验先整体动作与画布再看细节)。

同一段动画的所有帧、首尾帧和相接片段必须使用一致画布、角色尺度和锚点；不同动作不必统一为最大的生成画布。需要在游戏里对齐时保留各自锚点／偏移，或在导出阶段按项目约定组织统一单元格，不为此降低生成阶段的主体占比。生成后复查全程运动范围和无效空白；如需裁边，应保留原件、整段统一裁切且不缩放，不逐帧自动紧裁造成抖动。用户要求保留现有画布时，只改后续准备方式。

V2 的 `--padding`／`--padding-alignment` 与旧动画入口的四向 padding 不是同一组参数。需要不对称留白时，先在本地准备画布，提交时避免重复加 padding。Pixel 与 HD 的输入限制分别按[动画参数与输入检查](../../references/animation-and-video.md#frame-animation-new)执行；像素专属尺寸建议见[像素动画约束](pixel.md#3-动画制作与像素专属约束)。

### 生成动画前，先让用户确认输入图

姿态、背景和动作画布准备好后，展示实际将提交的首帧；使用首尾帧时将两张图一起展示。简述动作方案、画布尺寸与留白用途，等用户确认后再生成动画。用户已确认这组最终输入图时无需重复询问；仅认可角色造型不等于确认了后续动作的首尾帧。

## 3. 多方向优先复用，必要时做八向图

目前分别生成不同视角的动画，难以确保动作和时序完全一致；提示词可限制动作、节奏和镜头，但不是一致性保证。左右可镜像且玩法允许时，优先生成一个方向后镜像复用；横版过关角色常可因此只做一个朝向。镜像会翻转装备、尾巴和左右手，需符合角色设计。

确实需要多角度时，先用角色八向图功能（`character-multi-view-run`）统一各向造型和起始姿态，再分别生成动作并逐向验收。八向图解决方向参考，不自动保证八向动画同步；对不能镜像的非对称角色，按[八向角色说明](../../references/pixel-and-hd-assets.md#eight-direction-characters)准备非镜像视角。

## 4. 生成小样：高帧率与分辨率

对 Agent 工作流，按已确认的背景与用途选择高帧率，不统一开启：

| 背景与用途 | 高帧率建议 | 去背景安排 |
|---|---|---|
| 绿幕动画 | 开启 `--high-frame-rate`，保留全部生成帧 | 生成时关闭付费抠图，后续处理绿幕 |
| 不用绿幕，但需要去背景 | 推荐关闭高帧率，不传 `--high-frame-rate` | 按实际素材选择去背景方式，减少逐帧处理量与费用 |
| 宣传展示，无需去背景 | 开启 `--high-frame-rate` | 显式设置 `--remove-bg-method none`，保留已选背景 |

背景按生成前已确认的用途选择：需要免费绿幕抠图时使用绿色，后续将资源导入 [Meowa 官网](https://meowa.ai/) 的免费抠图工坊；宣传展示且无需抠图时建议白底。绿幕颜色应避开主体颜色，绿色角色可换成能分离的纯色并另验收抠图。独立发光特效可用纯黑背景，再做色度／亮度抠图并保留软透明；主体有重要黑色区域时不能把黑色直接全部删掉。输入背景也需处理为目标纯色或透明，不能只在提示词里要求背景色。

**控制大面积特效，不追求完全没有特效。** 身上放电、武器变色、局部发光等贴着角色的小特效通常不影响使用。需要避免的是冲击波、气浪、光柱、大片粒子等大面积特效：它们容易超出画布被截断，也难以和背景干净分离。提示词可写明“不要大面积特效，冲击波和光芒不要超出画面”，大范围效果交给游戏代码或单独制作的特效素材。目前的模型无法完全禁止特效，结果里仍可能出现；只要不影响使用就不必反复重生成，先给用户看效果再决定。

高帧率模式本身不额外收取生成费用；如果同时启用付费抠图，按实际帧数计费，费用可能增加。教程示例显式关闭生成阶段抠图，保留绿幕供后处理；CLI 抠图是独立计费能力，不能等同于网页免费工坊。

按目标选择**动画生成分辨率**：

- **方向未定时先低成本探索。** 用户尚未确定动作、提示词或设计方向时，可在已授权预算内用 480P（`--resolution 480p`）做少量快速试作，获得提示词和设计灵感；确认方向后再用较高分辨率制作最终版。若 480P 结果已经满足质量要求，直接采用，无需默认升级重做。
- **质量优先时尝试 720P 与 1080P 快速版。** 提高生成分辨率通常能改善 Pixel 的动作清晰度、像素稳定性及 HD 细节，尤其有助于约 200×200px 及以上的较大像素角色。可结合预算尝试 720P 或 1080P 快速版（Speed，`--resolution 1080p`，非 Full），按实际效果选择。
- **权衡 Speed 与 Full 的稳定性和耗时。** 1080P Full（`--resolution 1080p_full`）通常比 Speed 更稳定，但生成明显更慢，不作为默认选择；时间允许且更重视稳定性时可考虑。Speed 偶尔会出现背景色闪烁，需完整回放检查，不能只凭单帧判断背景稳定。

生成分辨率与角色图的原始尺寸是两个概念，不需要为提高分辨率先放大输入角色；更高分辨率也不能弥补不合适的首帧。

以下是高清单次攻击示例；像素素材将 `--style-mode hd` 改为 `pixel`，并先核对[像素输入与预览约束](pixel.md#3-动画制作与像素专属约束)。单次攻击使用非循环动作设计；行走等重复动作按用途选择 `loop`。

```bash
python3 skills/game-assets/meowart_api.py meowa-animation-run \
  --image-file <approved-attack-pose.png> \
  --prompt "角色向右挥剑一次，回到蓄力姿态，镜头固定" \
  --style-mode hd --resolution 720p \
  --output-frames 16 --animation-mode non_loop \
  --high-frame-rate \
  --remove-bg-method none --background-color '#00b140' \
  --optimize-prompt \
  --output-dir ./outputs/knight-attack-animation
```

高帧率下 `--output-frames 16` 选择约 2 秒时长档位，不是要求最终只保留 16 帧；实际帧数和时序以下载结果为准。保留默认提示词优化，音效描述可留空，由优化步骤提炼主要声音。

提示词优化可能丢失细节：复杂动作可能被简化，或缺少原本要求的停顿、顺序与关键姿态。复杂动作在提示词里写清招式顺序、每招之后的停顿和必须出现的姿态；生成后若发现这些内容缺失，把它们补充进提示词再试，必要时措辞写得更明确。确认提示词已经是最终版本时，可用 `--no-optimize-prompt` 原样提交。

模型只支持固定时长档位，按近似时长理解：用户要求 4 秒，实际得到 3.75 秒属于正常结果，不据此判定失败或默认补帧、变速、重做。交付时记录实际时长；只有项目明确要求精确时间轴时，再按项目要求处理。

变身或特效出现时，改为首尾帧控制，例如：

```bash
python3 skills/game-assets/meowart_api.py meowa-animation-run \
  --image-file <original-form.png> \
  --last-image-file <transformed-form.png> \
  --prompt "骑士被火焰包围，变为尾帧的火焰铠甲形态，镜头固定" \
  --style-mode hd --resolution 720p \
  --output-frames 24 --animation-mode non_loop \
  --high-frame-rate \
  --remove-bg-method none --background-color '#00b140' \
  --optimize-prompt \
  --output-dir ./outputs/knight-transformation
```

特效出现时，将首帧换为同尺寸空白帧、尾帧换为特效图，并简短描述出现过程。首尾帧默认约 3 秒，示例显式使用该档位，避免过短导致中间冻结。具体分辨率、质量、抠图和音频行为见 [V2 参数说明](../../references/animation-and-video.md#frame-animation-new)。

## 5. 连续动作与分段拼接

先确定游戏要怎样使用动作，再选生成方式。**一次按键对应一招时，交付应是可独立播放的单招；不应把直拳、上勾拳、下勾拳绑成必须播完的整段。** 这不要求每招都单独调用生成：可以分别生成，也可以在一段中制作清楚分隔的动作，再拆成单招。

| 制作方式 | 适用情况 | 主要验收点 |
|---|---|---|
| 每招单独生成 | 每招需要不同起手、力度、时长或画幅，或某一招需要单独迭代 | 每段只做目标招式，并有完整起手与收招；不同段的外观、尺度和准备姿势能衔接 |
| 连续生成后拆分 | 同一角色、同一站位的一组动作，希望共用近似准备姿势 | 动作间有收势停顿，招式没有粘连，拆开后每段仍完整、可独立使用 |
| 整段连续播放 | 游戏本就需要不可中断的整套连招，或用于演出 | 动作顺序、整体节奏及起止状态正确，不把它误作独立单招 |

### 连续生成后拆成单招

制作可拆分的原地攻击时，提示词说明角色朝向、站位和招式顺序，要求**每次只攻击一下，随后收回近似相同的准备姿势，短暂停顿，再开始下一招**。例如：“角色面朝左侧，原地依次打一记直拳、上勾拳、低位勾拳；每招后回到双拳胸前的准备姿势，停顿约0.2秒，再出下一招，镜头固定。”停顿时长只是起点，需在实际帧率下看是否留出了清楚切点；拳头伸在外面停住，不等于完成收招。连击这类单次动作生成时使用 `--animation-mode non_loop`，避免为了回到首帧而多出冗余的还原帧。

每次出招可以有必要的重心变化，但应检查角色是否逐招向前漂移、脚底高度是否改变、身形与准备姿势是否越变越多。提示“原地不动”不保证锁定站位。格斗动作允许多少踏步或位移取决于设计；需要严格固定时，不能把明显漂移的片段直接当作合格原地动作。

先按[动画校验](#6-动画校验先整体动作与画布再看细节)判断整段动作与画布是否正确，再找各招之间已收势、姿态稳定的停顿区间作为切点。逐段回放，检查它能否独立起手、完成一次攻击并收招，再与准备姿势或其他招式试接。不要只按时长均分，也不要因为原片视觉连贯就假定拆开也可用；没有可用停顿、招式粘连或动作错误时，改制作要求或单独重做有问题的一招，不强行拆成成品。保留原片和切分范围；裁剪时保持像素、画布和所选帧的原时长，对应音效与背景版使用同一时间范围。

两条路线没有固定的胜负。一次原地格斗招式试作中，带收势停顿的连续版比独立生成的上勾拳更容易得到可拆分结果，但这只是该角色与这组动作的经验。首次制作可在授权预算内用少量动作比较实际招式、收招、站位与切点，再扩展整套；不要把一次生成的成败当作普遍成功率。

### 复杂过程分段生成，再拼接

跳起、飞扑、下砸等复杂过程可选约4秒，给蓄力、腾空、攻击和落地留出时间，再用简洁提示词交代顺序。V2使用`--output-frames 32`选择约4秒档位；开启高帧率后保留实际生成帧，32不是最终帧数。时间更长提供动作空间，但不保证每个阶段正确；需要限定终点时加尾帧。

连续复杂动作可拆成共享关键姿态的三段首尾帧生成：

| 段落 | 首帧 → 尾帧 | 示例过程 |
|---|---|---|
| 1 | A → B | 站立蓄力，跳到空中 |
| 2 | B → C | 从空中挥击，落到地面 |
| 3 | C → D | 落地收势，回到待机 |

先用万能编辑准备A、B、C、D并统一画布、背景、尺度和锚点；前一段尾帧与后一段首帧复用同一张已验收图片，每段用`--last-image-file`控制终点。分别按复杂度选时长，不必每段都4秒。三段验收后按原时序拼接，检查接点是否跳位、停顿或速度突变；共享端点约束姿态，仍需检查运动是否连贯。循环目标可让D复用A，并另验收末尾到开头的衔接。

### 投掷与组合动作

投掷道具或角色、替身合击等组合动作，在游戏里由逻辑实时组装，生成前就要按组装方式准备首尾帧。准备方法和生成后的处理见[帧动画后处理：组合动作](../frame-animation-postprocess/combo-assembly.md)；连击加速、裁掉抬手与还原帧等节奏处理见[加速与裁帧](../frame-animation-postprocess/speed-and-trim.md)。

## 6. 动画校验：先整体动作与画布，再看细节

生成后先快速完整回放，做必要的初步检查，再将原始动画或轻量预览展示给用户，简述效果、主要问题和建议方案，例如直接采用、扩大画布重生成或局部整理。先征求意见，等用户确认处理方向后，再投入大量逐帧排查、修边、抠图或打包，减少无效工作与 token 消耗；预览不标为已验收成品。

后续详细验收时，**先判断这是不是所需动作、动作是否完整、有没有不可接受的裁切，再关注小瑕疵。** 建议按以下顺序验收：

1. **整体动作与用途。** 招式、方向、次数和顺序是否正确，起手、主要发力与收势是否齐全；行走／奔跑的步态是否成立，跳跃是否包含起跳与落地。上勾拳变成踢腿、一次攻击变成多次攻击、关键阶段冻结或缺失，都属于整体不合格；不应先花时间修小像素或抠图边缘。
2. **运动范围与裁切。** 检查头、手、脚、武器及需要完整保留的特效，在最远动作处是否碰边或被截断；同时看是否有明显多余留白。按用途判断能否接受：少量火花、光点等次要特效略微出画可以接受，不因碰边就一律重做；扔出的瓶子飞出边缘也可以是预期。人物的手、脚或主要攻击效果被切掉则应提出处理方案，不用局部修边掩盖缺失动作。
3. **角色与画面稳定性。** 检查脸、体型、服装、道具和配色是否保持，背景是否持续符合要求，站位、脚底高度与角色尺度是否有明显漂移。凭空出现领带、背景从绿幕变色或身形明显缩小，都需要单独说明并处理，不能只因文件生成成功就通过验收。
4. **局部质量。** 前三项满足用途后，再检查像素抖动、偶发亮帧、轻微轮廓变形、特效残留与音画同步。按实际游戏尺度判断影响，不让不影响使用的小瑕疵盖过整体动作是否可用。

画布不足造成不可接受的裁切时，优先沿越界方向扩大输入画布，保持角色尺度、统一首尾帧尺寸，在入口尺寸限制和已有预算内重新生成一次并复核；不要只给已裁切的成片补边。更新后的输入图和重生成方案仍按上述流程交用户确认。其他整体动作问题再按原因调整姿势、动作描述或时长，不直接扩大整批生成。动作通过后，再进入拆分、循环整理和背景处理。任何整理或抠图之后都要重新回放，确认没有损坏已通过的动作。

## 7. 循环动作整理

循环整理适用于行走、奔跑、待机等需要不断重复的动作。WebP带有循环播放标记，或生成时选择了`--animation-mode loop`，都不代表首尾已经连贯；单次攻击和首尾帧过渡也不应为了循环而删掉必要的起手或收势。

1. **先找不连贯的原因。** 完整播放原片及末尾接开头的过渡，再查看步态各阶段。区分起步过渡、多余停顿、重复动作、首尾阶段不匹配与本身错误的动作；奔跑常有开头从准备姿势进入跑姿的额外帧，行走也可能有起步或重复阶段，不要只检查奔跑。
2. **按完整周期选帧。** 选择姿态、运动方向、速度和身体位置能自然衔接的一轮或多轮动作，裁去确实破坏重复节奏的前后过渡。不要只因首末截图相似就决定切点，也不要为了凑8／16／24帧而删帧；步态阶段和动态衔接比目标帧数重要。
3. **保持时序与像素。** 保留下载原件，另存整理版并记录保留帧范围。保持所选帧的原始时长、画布、alpha和像素尺寸，不默认插帧、变速或缩放。对应背景版用同一组帧；独立WAV按保留帧对应的起止时间裁剪，不能只改动画而让音效错位。
4. **重新连续回放。** 至少看几个循环，检查接缝是否跳位、突然加速／停顿、闪亮或出现异常脚步节奏。开头一两帧只有确属异常亮帧且不承担必要动作时才移除；裁帧不能修复错误步态或严重变形，仍不合格时应回到动作制作，而不是强行标成无缝循环。

## 8. 抠图、复核和交付

通过整体动作与画布校验后，再按已确认的用途处理背景。白底宣传素材无需抠图；需要透明素材时，Agent可在本地从已声明的最终动画做绿幕抠图，保持画布、锚点、时序和像素边缘；检查绿色残边、主体误删和半透明特效。需要半透明火焰或光效时，不要把有意义的软alpha全部二值化。也可交由用户使用官网免费抠图工坊；保留绿幕交付也是一种明确的资产选择，不能称为透明成品。

若生成动画的背景色在帧间乱变，导致难以干净抠图，应尽早考虑在已有授权和预算内重新生成，避免反复强抠损伤主体。用户追求最高质量时，优先重新生成并检查背景是否稳定。也可以先另存一个尽力抠图的候选版本，展示残留、轮廓损失等问题，请用户确认是否可以接受，再决定采用；未经确认不作为合格成品。不能根据一帧背景色假设整段都是同色幕。

保留下载原件，清理或拆分结果另存。重新回放最终文件，核对实际尺寸、帧数、总时长、alpha、边缘和动作完整性；Pixel 预览用最近邻整数倍放大，HD 保留平滑边缘；不要把高清软透明套成像素硬边。若有独立WAV，检查与最终动画的时长和主要声音同步，不能宣称WebP内嵌音频。

**同一角色的一套动作还必须做跨动作位置验收。** 不同 padding 会使角色相对画布中心偏移，单段正常不代表切换时不会瞬移。交付前读取[帧动画处理：跨动作锚点验收与位置矫正](animation-alignment.md)，先 review，再决定是否为每段应用固定平移并补 padding，统一身体根锚点与地面线；已对齐则无需矫正。保留跳跃、击退等真实运动，不逐帧按重心居中。

将验收后的最终动画登记到本地`final_outputs.json`再交付；提取帧、掩码、调试文件和上游角色参考图不作为动画最终交付物。对保留的局限和参考候选明确标注，不把未通过的招式包装成合格单招。通用下载与恢复规则见[运行与产物规则](../../references/running-and-outputs.md)，V2参数及模式边界见[动画与视频](../../references/animation-and-video.md)。

用户要求导出到指定目录时，先按[动画导出](animation-export.md)确认游戏资源或宣传资源用途，再整理格式、尺寸与音效。
